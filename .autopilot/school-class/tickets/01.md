# 01 — Аккаунты и пространство класса

Требования: R02, R03, R04, R12i, G02, G03
Blocked by: []
Волна: 1
Зона: server/core, src/core, src/features/classroom, root config, tests/auth.test.mjs

## Из брифа
«мобильное приложение для школы»; «веб версию и приложение, с реалными аккаунтами»; «список учеников и их анкетные данные, расписание уроков, звонков»; «домашние задания»; «получать ачивки, баджи»; «Учитель тоже может выдавать награды».

## Разделы спецификации
Истории и приёмка (указанные требования), Реализация, Границы и швы.

## Что должно заработать и критерии приёмки
Создай готовую основу приложения: Node/Express/SQLite с auth, регистрацией взрослых, приглашением родителей, созданием учеников учителем, сменой пароля, операторским одноразовым восстановлением, классами и анкетами. Настоящая файловая база и серверные проверки. Одновременно создай качественный адаптивный React UI: вход/регистрация/принятие приглашения, выбор класса и ребёнка, создание класса, список и форма ученика, профиль/смена пароля. Дизайн: светлый тёплый фон, чернильный текст, фиолетовый основной цвет и мягкие мятные/персиковые акценты, крупные аккуратные карточки, lucide icons. Левое меню на компьютере и нижняя навигация телефона. Никаких выдуманных реальных данных; пустые состояния с действиями. Название Классно.
Создай ВСЮ схему включая lessons, bells, homework, completions, awards и необходимые индексы. Создай минимальные файлы server/schedule.mjs и server/homework.mjs с register*Routes(app,ctx), подключи в app. Создай src/features/schedule/SchedulePage.tsx, homework/HomeworkPage.tsx, homework/AwardsPage.tsx с временными EmptyState: их заменят T02/T03. UI shell уже маршрутизирует эти страницы. Через возвращённый INTERFACES контракт назови точные DTO/API/context и SQL columns для следующих исполнителей.
Разрешены зависимости react/react-dom, vite, typescript, lucide-react, express, supertest и их типы, capacitor core/cli/ios/android8; и небольшие необходимые средства запуска. Предпочти .mjs сервер и node:sqlite без native install. Сессии web HttpOnly/cookie+Origin check, mobile bearer в памяти (не localStorage). Продумай доверенную отличимость bearer режима, CORS и production default fail closed. При создании учеников логины уникальны глобально, учитель задаёт начальный пароль; не возвращать сохранённые пароли. Приглашения одноразовые с истечением и криптографической энтропией, привязаны к studentId. Родитель видит только своих детей. Нельзя разрешать вход в чужой класс по его id.
Критерии: (1) взрослый регистрируется, входит, выходит; смена/сброс пароля отзывает сессии; (2) учитель создаёт класс и ученика; ученик входит; (3) родитель принимает персональную ссылку с аккаунтом/регистрацией, видит ребёнка; (4) приватные заметки и чужие анкеты не выдаются; (5) два класса и семьи изолированы через API; (6) данные сохраняются после reopen SQLite; (7) production web build и HTTP integration tests auth/roles зелёные; (8) адаптивные формы и навигация доступны с клавиатуры. Документируй контракты подробно в отдельном core-contract.md в корне (разрешён), кратко в return. Никаких реальных auth секретов в документах/ответах.
